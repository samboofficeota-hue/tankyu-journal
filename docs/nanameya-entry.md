## 5. ログイン — 生徒（メアドがない前提）★ここが本題

### 前提の確認

ジャーナル側の現行ログインは「学年・組・番号を選ぶだけ」で**パスワードが無い**。
記録を書くだけならこれで成立するが、ナナメの部屋は**外部の大人との1対1**が起きるので重みが違う。
他人の番号で入って予約すると、**他人の探究カードが大人に渡る**。

もう1つ大事な前提。**認証を置くと、エスラボが「誰が誰か」を持つことになる。**
[privacy](nanameya-privacy.md) は「大人に渡るのは学年＋ニックネームまで」で設計している。
ログインの作り方しだいでこの土台が崩れる——**認証層まで同じ思想を貫けるかが選定基準**。

### 3案

| 案 | しくみ | メアド | エスラボが持つ情報 | 学校への依存 | なりすまし |
|---|---|---|---|---|---|
| **A 招待コード＋PIN** ★推奨 | 先生が紙でコードを配る。初回に生徒が4桁PINを決める | 不要 | **乱数コードと学年だけ**（氏名・組・番号を持たない） | コードを配る運用のみ | 低 |
| B 学校のGoogleアカウント（SSO） | GIGA端末のアカウントで入る | 不要 | 学校ドメインのアカウント＝実質の個人特定 | 高（区の規程・IdP設定） | 低 |
| C ジャーナルと同じ 学年・組・番号 | 現行踏襲 | 不要 | **名簿そのもの** | 名簿の受け渡しが必要 | **高（誰でも他人になれる）** |

> **2026-09-05 の判断：いったん案Cで組む。** 個人情報保護は最後にまとめて対応する方針のため、
> ここでは止めない。ただし §0 の⚠️ を必ず残す。以下は、まとめ対応のときに戻ってくるための記録。

### 推奨がAである理由

1. メアドが要らない（前提を満たす）
2. **エスラボが実名名簿を持たなくて済む。** privacy.md の許可リストの思想を、認証層まで同じ形で貫ける
3. **S3の保護者同意ゲートが、画面のフラグから「コードを配る／配らない」という物理ゲートに変わる。**
   同意が取れた生徒にしか先生がコードを渡さない運用にすれば、C4の目標「同意なしの予約ゼロ」が
   **運用ではなく構造で**担保される
4. 学校のIdPに依存しない＝2校目以降の交渉材料が1つ減る

### Aの弱点と手当て

| 弱点 | 手当て |
|---|---|
| コードを失くす | 先生が再発行。**「誰にどのコードを渡したか」の対応表は学校側が持つ**（管轄の線を守る） |
| コードの又貸し | 技術で止めきれない。同意ゲート＋通報導線＋事務局が同じカードを見られること（privacy §3）で抑える |
| 共有端末でログアウト忘れ | 一定時間で自動ログアウト。※端末が個人持ちか共有かは先生に要確認（§7-3） |

## 6. ログイン — 大人・事務局

1. **大人（C6）はメアドがある** → パスワードレス（メールに届くリンク）が妥当。
   **承認済みの人だけがログインできる**こと。審査中のC5は入れない（privacy §4）
2. **募集ページ（V0-1）はログイン不要**、応募ステータス（V0-3）はログイン必要。C5は「まだ誰でもない」状態で入ってくる
3. **事務局（C4）の入口はポータルに並べない方がよい** — 別URL・別ログイン。
   いまポータルの5枚目に出ているが、生徒も見る画面に管理画面の入口を置くことになる。★判断がほしい

## 7. 先生に聞くこと（相談リスト）

1. 生徒はGIGA端末のGoogleアカウントを持っているか。**外部サービスのログインに使ってよいか**（区の規程）
2. 紙のコードを配る運用は現実的か。誰が配り、失くしたとき誰が再発行するか
3. 端末は**個人持ちか共有か**（共有なら自動ログアウトが要る）
4. 使うのは学校からだけか、家からもか
5. 保護者同意は何で取るか（紙／連絡アプリ）。「同意が取れた」を**誰が確定させるか**

## 8. データ設計への波及（★既存ドキュメントの修正が要る）

[`nanameya-flow.md`](nanameya-flow.md) §5 は `bookings` に
**`student_grade` / `student_cls` / `student_no`**（既存 `entries` と同じ主キー構成）を持たせている。

これは §5 の案Aと両立しない。というより、**管轄の線（判断D-2）とも整合していない**——
ナナメの部屋のテーブルが、学校の名簿キーをそのまま持つことになる。

案Aを採るなら:

- `bookings.student_*` → **`student_id`**（ナナメの部屋側の乱数ID）に置き換える
- 新テーブル `students`: `id` / `school_id` / `code_hash` / `pin_hash` / `grade` / `nickname` / `consent_at`
  ※ **氏名・組・出席番号は持たない**
- 新テーブル `auth_sessions`: `token` / `role` / `subject_id` / `expires_at`
- 探究カードの元データは、**生徒がログイン中に自分で持ち込む**（ジャーナルから生徒の操作で渡す。
  エスラボが横から読むのではない＝nanameya.md 1-4章）

→ 方式が決まった時点で `nanameya-flow.md` §5 を差し替える。
